## 1. Verdict

**A reduced version should work; I would not build v4 exactly as written.** The storage choice, deterministic filters, and bounded ReAct loop are credible, but beating a strong baseline remains unproven. Four-hour startup is plausible with the embedding cutoff; four concurrent answers within 180 seconds still need a real API test. The full scope is too large for seven hours, and several interface gaps can silently lose evidence. This was a read-only review with corpus measurements, not a runtime benchmark.

## 2. Findings

1. **High — The forced-finish deadline is internally inconsistent.**  
   [plan.md](docs/runs/2026-10-14-rag-system-plan/plan.md), §4.6: ordinary turns use `time_left − reserve`, but forced finish starts when less than the reserve remains. Applying the same timeout formula then gives zero or negative time. A finish, retry, fallback, and repair also cannot each spend the same reserve.  
   **Change:** Define separate exploration and finalization budgets beneath one absolute deadline. Include limiter waits, query embeddings, retries, verification, and serialization. Permit another network call only when its budget fits; otherwise return the deterministic error response. Test four concurrent requests with slow calls and 429s.

2. **High — Metadata is stored but not reliably discoverable.**  
   [data-and-retrieval.md](docs/runs/2026-10-14-rag-system-plan/data-and-retrieval.md), §§2.1, 3.1: cards contain catalog fields, generally present in ≥20% of documents. Short, rare metadata therefore reaches neither cards nor extra body blocks. `field_values(source, field)` cannot discover an unknown field name. The corpus study reports 1,910 keys appearing in only one document.  
   **Change:** Index all non-plumbing metadata in searchable overflow chunks, independently of prompt/catalog limits. Add field-name discovery. Apply long-text handling to lists too: fields such as action items must not disappear because their profile says `list`, not `text`.

3. **High — The revised temporal rule reintroduces a previously accepted problem.**  
   Plan §4.4 permits plausible recency to establish the current value; data design §2.1 derives `doc_date` from creation dates. These are insufficient for authority or event timing. I checked tune question `pub_0051` against its documents: a March 24 customer email contradicts a published standard updated March 8 that explicitly calls itself the current reference.  
   **Change:** Establish applicability, authority, explicit supersession, and approval before using recency. Preserve named dates in observations. Date filters must distinguish creation, update, and event dates; unknown dates should not silently exclude potentially relevant evidence.

4. **High — The new citation schema cannot represent its verification promises.**  
   Plan §§4.3, 4.8: one claim can cite multiple documents but has only one quote. Aggregate claims reference `R#` without identifying a group, so citing one group can expand to every document in the aggregate. Quote checking targets stored text, while metadata-card evidence has no clearly specified verification representation.  
   **Change:** Use `evidence[]` entries containing document handle plus passage or field/value, and explicit result-set/group handles. Verify against the evidence actually exposed. Make answer spans reference validated claims so failed evidence removes or repairs the associated prose deterministically. Quote matching alone does not establish entailment.

5. **High — Complete evidence sets are retained internally but cannot always be read.**  
   Plan §4.3 caps filters at 50 rows and reads at roughly 6K tokens; neither interface exposes a cursor. Data design §5.1 calls long reads “paged,” but there is no page argument. Complete citation IDs cannot compensate for missing names or unread narrative details.  
   **Change:** Add stable result-set and document cursors, with row handles and explicit exhaustion. Define filter operators, list membership, substring matching, and count units. Tune `pub_0043` needs a compound value containing “Zilliz,” not merely exact equality. Keep document counts distinct from entity counts.

6. **High — Stale eval instructions undermine the fixed split.**  
   Plan §10 still requests a “full 79-question eval”; §6.7 exposes `dev` and puts detailed results into a shared timestamp directory. AGENTS.md instead requires a user-named milestone and aggregate-only inspection of held-out runs. Shared request traces create another exposure path.  
   **Change:** Remove combined-dev execution, enforce the milestone in the runner, and isolate held-out results, traces, and reports behind the protected path. Apply the same controls to baseline runs. Do not regenerate the split.

7. **Medium — Identifier discovery is too brittle for cross-source joins.**  
   Data design §2.1 requires ≥90% field presence and short values. My scan found Gmail deal IDs in 3,939/4,957 documents and Fireflies CRM deal IDs in 377/440: both fail despite being useful references. Eleven meeting IDs exceed 40 characters. Under a strict all-values interpretation, two oversized Linear keys reject the entire key field.  
   **Change:** Treat these statistics as confidence signals, tolerate outliers, and retain ambiguous candidates. Infer ownership separately from reference fields. Do not infer a PR namespace merely because an arbitrary field makes pairs unique. For people, retrieve name/email/handle variants but require evidence before merging identities.

8. **Medium — Deduplication, compaction, and tool-call limits need one coherent protocol.**  
   Plan §4.5 says compacted evidence can be reread, but duplicate calls return only a pointer to the old turn. That makes removed evidence inaccessible. The plan also does not define handling for five returned calls, multiple finishes, or finish mixed with retrieval.  
   **Change:** Cache execution results but replay their evidence when requested. Return explicit outcomes for rejected calls and define finish precedence. Preserve signed model content through any history transformation, and test the exact SDK/model combination. Gemini supports parallel calls, and its thinking-state handling imposes history requirements. [Function calling](https://ai.google.dev/gemini-api/docs/function-calling), [thinking documentation](https://ai.google.dev/gemini-api/docs/thinking).

9. **Medium — Startup is feasible, but the throughput estimate is conditional.**  
   Data design §§2.4, 4 assumes roughly 1M embedding tokens/minute. Completing 32M tokens within the two-hour embedding cutoff requires approximately **267K tokens/minute**, before retries and overhead. Project quotas and available capacity vary. [Rate-limit documentation](https://ai.google.dev/gemini-api/docs/rate-limits).  
   **Change:** Benchmark sustained throughput and record actual quotas. Keep the cutoff, but distribute partial body coverage across sources. Validate response count/order, dimensions, finite values, and norms. Pin the embedding adapter: “001 or newer” is unsafe because Embedding 2 changes task specification and multi-input aggregation. [Embedding migration documentation](https://ai.google.dev/gemini-api/docs/embeddings).

10. **Medium — Eval attribution currently overstates certainty.**  
    Plan §6.6 labels the “first” failure, but `retrieval_miss` also matches ranked-out or deadline-stopped cases. Documents supporting an aggregate may never appear individually in observations. An extra citation is not necessarily unsupported simply because it is absent from the gold set.  
    **Change:** Separate observed symptoms from inferred causes; allow multiple labels. Track candidates, shown passages, result-set provenance, cited evidence, and stop reason separately. Report exact gold citation scores alongside audited support judgments. Add paired uncertainty estimates and repeated close comparisons; 30 tune questions cannot establish unseen-corpus generality.

11. **Medium — The cost estimate is plausible, but not a complete budget.**  
    Plan §4.10 counts input tokens while leaving thinking, output, judging, retries, and repeated tuning implicit. At published Gemini 2.5 Flash rates, 125K input tokens cost about **$0.0375**; another 25K output/thinking tokens cost **$0.0625**. [Pricing](https://ai.google.dev/gemini-api/docs/pricing).  
    **Change:** Budget all phases and reserve grading spend. Enforce limits before dispatch, including concurrent reservations. $500 looks workable for bounded Flash runs; it does not justify unlimited model comparisons or large-context retries.

## 3. Cut list

- Defer incremental generation updates, migration machinery beyond a schema version, process-pool parsing, critic nudges, synthetic questions, and broad parameter sweeps.
- Defer context compaction; start with smaller evidence budgets and reliable rereads.
- Keep traces, but build a minimal viewer and straightforward failure flags first.
- Build order: executable contract shell and API probe → generic loader/FTS plus baseline → bounded loop and structured tools → embeddings if measured retrieval improves.
- Reserve the final 90 minutes for checks, four-request latency testing, fresh-clone execution, and `SOLUTION.md`. The first-hour deliverables in §10 are substantially overcommitted.
